## B1 - D213 (b): one-row Run strip from about 1280 px - DONE

`_RunStrip` (`ui/run_panel.py`) used to split one-row space by a fixed 23:10 stretch
ratio (Progress : each tile), so at 1280 x 840 the predicted P MAX share (about 111 px)
fell short of its measured need (125 px) and the strip wrapped to two rows, even though
roughly 240 px of slack sat unused in Progress at `PROGRESS_MIN` (220 px). Rebalanced by
widths instead: `_one_row_fits` now sums P MAX's measured need (`_pmax_need()`,
unchanged font-metric logic), `TILE_MIN` (112 px, unchanged) for every other shown
tile, and a new, lower one-row floor for Progress, `PROGRESS_MIN_1ROW = 160`. `arrange()`
sets these as real `setMinimumWidth()` values on each tile only while one row is chosen
(cleared to 0, and Progress's floor set back to `PROGRESS_MIN` = 220, on the two-row
branch), so the widths the fits check promises are the widths Qt actually gives; the
23:10 stretch factors are unchanged and only share space above the floors.

`PROGRESS_MIN_1ROW` = 160 px was picked from a measurement, not guessed: the Progress
tile's head (`PROGRESS` caps + a `100 %`-wide percent label, margins included) needs
about 158 px to stay unclipped once the time line below it elides (it already does,
`QSizePolicy.Ignored`); 160 px rounds that up by 2 px. With this floor the 3-tile strip
(AMR CELLS hidden, the board's default) goes to one row at window width 1220 px
(measured offscreen) - comfortably inside "about 1280 px" with ~60 px of margin, not at
the edge the old math left it. **P5** (approved): with CELLS shown (4 tiles) the strip
may still wrap at 1280; not required, not tested as a one-row case.

Because the floors never bind at generous widths (the old stretch-driven allocation at
1600 px already gave each tile more than its new floor), the existing 1600 x 1000
"Progress 2.3x a tile" layout pin (`test_ui_run_screen` R1, line 114-118) did not need
to change - measured after the change: still 2.304 (`394 / 171`), inside the pin's
±0.1 tolerance. No layout pin was moved.

## Engineering issues noticed

- K02 is hardcoded to 1100 x 720 (`qa.geometry('1100x720')`, the scenario's own
  docstring). The plan's acceptance item 3 asks for K02 "at 1100 x 720 and 1280 x 840";
  K02 itself only covers 1100 x 720 (ran, 0 findings). The 1280 x 840 case is covered
  instead by the real-platform script in acceptance item 2 (Win32 rects + screenshot),
  which is more precise for this specific claim (a strip-only check) than K02's
  whole-window "nothing clipped" sweep would be. Widening K02 itself to a second
  geometry is a harness change outside a low-risk, single-file layout task; flagging it
  here rather than editing `_qa_ui_harness.py` unprompted.
- Piping a long-running background harness through `| tail -N` (as the launch command in
  this prompt's own example does) buffers all output until the upstream process closes,
  so the redirected task-output file stays empty until the very end - not useful for
  interim progress checks. Reading the harness's own `checkpoint.json` / `harness.log`
  under `--out` directly (as it writes them) worked far better; worth a note for whoever
  next runs a background harness pass this way.
- `rp._readout` / `_render_readouts()` (used by the existing R12 sweep and by A1's
  R12 checks already in the file) is a convenient way to drive the strip with specific
  readout strings without a real solve; the real-platform evidence script used an actual
  tiny native 2D run instead, per the plan's "a native 2D run" wording, but the two
  produce visually identical strips - worth knowing for anyone who needs a cheap repeat.
