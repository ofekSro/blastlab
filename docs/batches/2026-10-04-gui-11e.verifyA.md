## Defects

| Where | Severity | Status |
|---|---|---|
| `output/gauge_summary.py` 121-140 `_nearest_entered`: the greedy nearest match can pair a point with the wrong entered gauge. This happens when two entered gauges sit within about a cell of each other and the earlier one was dropped, because the dropped one can be nearer the survivor's cell centre. The solver keeps the entered order, so an order-preserving match would be exact. It is the same rule as `ui/run_gauges._match` (plan P4, D201), so labels and screens still agree. | low | not fixed; within the plan's specified rule (engineering question 1) |
| `tests/test_case_validate.py` 623-625: the original 3D face checks are cross-checked against the solver for native only, because the blastFoam plan there is about 28 M cells. My probe covered 3D blastFoam faces instead (V3D, 0 mismatches). | low | not fixed (test coverage note) |

There are no silent failures in the diff. `_gauge_drop_rule` catches only
Arithmetic / Value / Type / Index errors and falls back to the open box, which is
documented. Nothing touches widgets off the GUI thread, no callers were left behind,
and nothing was left over.

## Engineering questions

1. Should F42's pairing (and `run_gauges._match`) become order-preserving? That would
   be a subsequence alignment of the points against the entered list, in place of
   greedy nearest. It is exact by the solver's construction, but it would change both
   the screens and the exports in the rare case above. Backlog together with the
   P4 shared-helper line.
2. In the plan's list of four flips, (1.2, 0.3) in 2D native is a tie on a cell face.
   Whether it is dropped depends on float rounding of `x_c` (here the fluid centre
   wins). The warning follows the solver either way, but a check on an exact face tie
   is fragile across grid changes.
