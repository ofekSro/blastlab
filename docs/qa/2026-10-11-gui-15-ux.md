# GUI-15 backlog - UX review (read-only)

- **Date:** 2026-10-11. **Tree:** `master` at `f1f9dd4`, batch range `48d59f9..f1f9dd4`.
- **Plan:** `docs/batches/2026-10-11-gui-15-backlog.md`, with the A/B implement and verify reports
  next to it. **Previous review:** `docs/qa/2026-10-11-gui-14-ux.md` (F1-F6, the sources of this batch).
- **Question:** is a dropped gauge now shown the same way from Setup through Run to Results and the
  exports, in 1D, 2D and 3D?
- **Method:** I read the batch diff and its call sites. Two scratch scripts call the pure functions
  and two offscreen widgets on the batch's own fixtures (scratchpad `ux15_probe.py`,
  `ux15_alldrop.py`). I opened no real window and ran no solve, so this review makes no geometry
  claim (CLAUDE.md §8.7).
- **Owner rule:** findings rated medium or higher become tasks. Low findings go to §6, Parking.

**Short answer: on screen, mostly yes. In the exports and on the side paths, not yet.** Checks,
the tree, Run from Start, the native log and Results now give the same number, wall and words for
a gauge dropped in 1D, 2D or 3D. Six gaps remain, all rated medium, and two of them are new
(introduced by A1):
- a trigger on a dropped gauge is still described as active on four surfaces;
- the 1D exports renumber the kept gauges;
- Resume and Run-browser Load lose the drop reason;
- blastFoam 3D takes back the drop at its first live payload (new);
- a case whose gauges are all dropped is told it has no gauges (new);
- the field plots draw a dropped gauge three different ways.

## 4. Findings (medium - each becomes a task)

No high findings. The batch makes no threading change and no input is lost.

**U1 - medium - 01 Setup (Checks, Gauges caption, trigger dropdown) and the chain HAND-OFF OUT
card - a trigger on a dropped gauge is still described as active.** This widens verifier open item 1.
- Where:
  - `validation.py:899-902`: the note `The run ends when the wave reaches gauge 2`. For `remap` it
    reads `Gauge 2 will write the remap file when the wave reaches it (the run then continues)`,
    but `jobs.py:65-72` writes no file.
  - `:1599-1607`: the D13 warning.
  - `setup_nodes.py:253-254`: the caption `· trigger G2`.
  - `case_form.py:407-447`: the dropdown lists `G2 · x 1.40, y 0.30` unmarked.
  - `chain_route.py:491-495`: `The field when the wave reaches G2 (trigger gauge, terminate), or at
    the end of the run.`
  - blastFoam: no warning (D13 is native only). `_trigger_cells` samples the entered gauge's cell
    (`backend.py:1785-1804`), and the behaviour is not measured (plan Q2).
- What the user sees: one warning against four statements that the trigger is live. On blastFoam,
  nothing warns at all. On a chain's 2D stage, the hand-off then happens at the stage's normal stop
  rather than at G2, so the 3D stage starts from a later field than the card promises.
- Why medium, when the verifier rated the Checks note low: the caption, the dropdown and the
  hand-off card repeat the claim, and in a chain the hand-off instant changes.
- Fix:
  - Add one predicate, `trigger_dropped(case)` = `trigger_gauge in sd.dropped_numbers(case)`.
  - When it holds:
    - Checks drops the note (the warning already says it);
    - the caption reads `trigger G2 (disabled)`;
    - the dropdown entry reads `G2 · … (dropped)` in warn;
    - `out_text` reads `The field at the end of the run (trigger G2 is dropped). …`.
  - blastFoam: settle it with Q2. Until then, warn there too, worded `the trigger may not fire`.

**U2 - medium - 03 Results exports, 1D - the PNG, the HTML report and the summary export renumber
the kept gauges and leave the drop out.**
- Where:
  - `plots.figure_gauges_1d:334` titles the panels `Gauge {k+1}`;
  - `gauge_summary.gauge_labels:98-100` labels 1D rows `G{k+1}`;
  - both are used by `services/exports.py:45-49, 182-191, 210-217`;
  - `results_gauges.export_drop_note:227-228` returns `''` for 1D.
- What the user sees (probe C): the screen shows G1, G3 and `G2 dropped by the solver (outside the
  domain)`. The exported figure says `Gauge 2 (r = 1.20 m)` for the 1.2 m gauge, the summary says
  `G2 r = 1.200 m`, and nothing mentions the 2.0 m gauge. This is F6's renumbering, moved into the
  file that goes into the thesis.
- Fix:
  - Add `numbers=None, drop_note=None` to `figure_gauges_1d` and `numbers=None` to the 1D branch of
    `gauge_labels`. The Qt export passes `labels_and_dropped(res, 1)`, and `export_drop_note`
    covers dim 1.
  - With `numbers=None` the output is byte-identical, so a run without a drop is unchanged.
  - The Tk export has no stamp: see Parking.

**U3 - medium - 03 Results after Resume or a Run-browser Load - the stamp is missing, so F3 and F6
come back.**
- Where:
  - `run_controller.resume_foam_run:150-164` calls `_launch` without `drops`, although the caller
    passes the run's own case (`app.py:1489-1503`);
  - `results_panel.load_foam_run_path:1137-1164` adds the post-mortem result unstamped;
  - `labels_and_dropped` then falls back to the face-snapped `meta['obstacles']`. The fallback is
    pinned at `test_ui_results_screen.py:1054-1063`.
- What the user sees:
  - A blastFoam run resumed after a WSL teardown (CLAUDE.md §8.3, W3) showed `within a cell of
    Wall 1` on Run from Start. After the resume, Results says `inside Wall 1`.
  - A 1D run opened from the Run browser numbers G3 as G2 and does not mention G2 (probe C,
    "reloaded").
- Fix:
  - `resume_foam_run`: `drops=[run_gauges.drops(case)] if case is not None else None`.
  - `load_foam_run_path`: on the worker thread, read the run's `case.json` as `_resume_foam_run`
    does and set `res.meta['gauges_dropped']` when it is non-empty. That is a pure function, so no
    widget is touched off the GUI thread.

**U4 - medium - 02 Run, blastFoam 3D - the drop named at Start is taken back at the first live
payload, and a row's label flips from G3 to G2 (Results flips it back).**
- Where: `run_gauges._numbering:230-231` (`_x_only_tie`) on the x-only live payload
  (`backend._gauges_from_probes:629-645`).
- What the user sees (probe B, the `test_ui_run_screen.py:1847-1857` fixture on blastFoam):
  - before any payload: rows `G1, G3`, line `G2 dropped by the solver (inside Wall 1).`;
  - live: rows `G1, G2`, no line;
  - Results: `G1, G3` and the line.
- Why this is new: before A1, the plain state held for the whole run (GUI-14 P6, parked as
  deliberate). Now the screen states the drop and then retracts it.
- When it happens: a dropped gauge at the same x as a kept one. For example, a column of gauges on a
  wall face at several heights, which is the usual reflected-pressure layout.
- Fix: the rule already knows which gauge is dropped, and the writer keeps the probes in entered
  order with the dropped ones removed (`writer.py:555-564`). When `_x_only_tie` declines but
  `len(pre_payload(case, rule)[0]) == n_series`, take series k as entered `kept[k]` and the line
  from `pre_payload`. This closes GUI-14 P6 too.

**U5 - medium - 02 Run (and 03 Results) - a case whose gauges are all dropped is told it has no
gauges.**
- Where:
  - `run_gauges.py:922-925` shows `NO_GAUGES` (`live_gauges.py:24-25`) when no row is left;
  - `:943` shows the drop line only `if has`;
  - `results_gauges.py:256`: `This result has no gauges.`
- What the user sees (scratch `ux15_alldrop.py`, offscreen):
  - the case has one gauge on the wall's face, which is the natural way to ask for reflected
    pressure;
  - Checks warns `G1 … within a cell of Wall 1 - will be dropped`;
  - Run says `This case has no gauges. Add one on the Setup tab to watch a point during the run.`,
    and the line naming G1 is built but hidden;
  - Results shows `This result has no gauges.` in the plot area, above a caption that names G1.
- Why this is new: before A1 the gauge showed as `waiting`.
- Fix:
  - When `not has and note`, show the drop line and replace the empty text with
    `Every gauge of this case is dropped by the solver - see the line above and Setup's Checks.`
  - Results' plot hint does the same whenever `dropped` is non-empty.

**U6 - medium - live field view and exported animation - a dropped gauge is drawn three different
ways.**
- Where:
  - native live: kept gauges only, with the trigger star (`solver2d.py:352`, `solver3d.py:434-436`);
  - blastFoam live: every entered gauge, with no star (`backend.py:1451-1452`, `:2104-2106`; no
    `trigger_gauge` in `run_info`);
  - exported animation, both solvers: every entered gauge, with the star (`animation.py:214-215`,
    `plots.gauge_points:112-136`). Probe D gives `[1, 2, 3, 4]` with G2 dropped.
- What the user sees: on a native run the live view shows G1 G3 G4. The GIF/MP4 from the same run
  shows G2 as well, as an ordinary marker inside the wall, with no footnote, while the gauge grid in
  the same export says G2 was dropped. On blastFoam the live view also draws G2 as if it measured.
- Fix: one marker rule for all three. The proposal is to draw the dropped gauge at its entered
  point, hollow and in the warn colour, labelled `G2 ×`; omitting it everywhere is the owner's call.
  - Give `plots.gauge_points` a `dropped=()` argument. The export passes
    `gauge_summary.dropped_numbers(res.gauges['points'], meta['gauges'])`.
  - The Qt live pane takes Run's `pre_payload` split.
  - Add `trigger_gauge` to blastFoam's `run_info`.
  - With nothing dropped the drawing is unchanged.
