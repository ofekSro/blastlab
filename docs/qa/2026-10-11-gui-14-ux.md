## 3. Findings (medium and above - each becomes a task)

No high findings. The batch adds no threading change and loses no input.

**F1 - medium - 02 Run - a dropped gauge shows as an ordinary `waiting` row until the
first payload.**
- Where: `run_gauges.py:315-318` (rows without a payload), `:880-887` (the drop line needs
  a payload), `:273-276` (the nearest wall).
- What the user sees: from Start until the first gauge payload, the dropped G2 sits in the
  list, and may be the enlarged card, as `Z … m/kg^1/3 · Wall 2 … waiting`. There is no warn
  line. On blastFoam that window lasts through blockMesh / setRefinedFields / the first
  write, which is minutes on a real case. Then the row disappears, the list re-sorts, the
  card jumps to another gauge, and the line appears. In the tie fixture the header even
  names a different wall (Wall 2) from Setup (Wall 1).
- Fix: in `_render` with no payload, build `drop_rule(case)` once, leave out the gauges
  `sd.is_dropped` flags, and set the drop line from `_drop_reason` straight away. That is
  the state the first payload would produce. For any row that stays, `_geometry` should
  pass `wall=dropped(p)` to `sd.where`, as `where_text` does. Add a check in
  `test_ui_run_screen.py`: after `set_case` with the e2e fixture, no `G2` row, the line
  names G2 and Wall 1, and the enlarged card is G1.

**F2 - medium - Native run log - the one surface that names no wall.**
- Where: `solver2d.py:288-292`, `solver3d.py:347-351`. D9 kept `an obstacle` because "the
  solid mask has no wall number".
- What the user sees: `[warn] G2 (1.40, 0.30) m inside an obstacle - dropped` (in Qt
  Messages, in `warn`), while Checks, Run and Results say `Wall 1`. For a gauge that
  blastFoam or native drops from *in front of* a wall, "inside" also contradicts Setup's
  `4 cm in front of Wall 1 (dropped)`.
- Fix: the solver has `obstacles` in the loop. The native drop rule is the closed test of
  the snapped cell centre on the raw boxes, first box wins (`validation.py:1713-1716`,
  `_in_box_closed :1720-1729`). So `n = first box containing (x_c[i], y_c[j][, z_c[k]])`
  is the wall number, a string-only change. Log `inside Wall n` when the entered point is
  strictly inside the box, else `on the face of Wall n`, as `gauge_drop_reason` words it.
  This is risk high (`solvers/`): kept-gauge arrays `array_equal`, regression
  byte-identical. Pin edits: `_e2e_gui_native_warn.py:61`, `_qa_gui_harness.py:1597`.
  Fix the vacuous check `:63-64` at the same time (implement-B issue 2).

**F3 - medium - 03 Results - blastFoam runs say `inside Wall n` where Run said `on the
face of Wall n` for the same run.**
- Where: `results_gauges.py:185-203` with `run_gauges._drop_reason:167-181` on face-snapped
  `meta['obstacles']` (`foam/backend.py:1690`). The scratch output (§2) shows this on all
  three blastFoam fixtures.
- What the user sees: during the run, `G2 dropped by the solver (on the face of Wall 1).`
  After the run, in the restyled warn line, `G2 dropped by the solver (inside Wall 1)`.
  Same gauge, same wall, but the reason changes, and "inside" is false for the entered
  geometry (the gauge is 4 cm in front).
- Fix: record the reasons at run start. The run controller already has the case:
  `meta['gauges_dropped'] = [[n, _drop_reason(case, p)], ...]`, computed in the UI from
  `drop_rule`, so no solver change is needed. `labels_and_dropped` prefers it and keeps
  today's fallback for older runs. A second-best option is to carry the entered boxes as
  `meta['obstacles_entered']` and run the open-box test on those.

**F4 - medium - 01 Setup - Checks and the Where cell use different words for the same
gauge on one screen.**
- Where: `validation.gauge_drop_reason:1600-1608` (`on the face of Wall n` for every drop
  that is not strictly inside) against `scaled_distance.where_text:255-264` (the measured
  `N cm in front of|behind Wall n (dropped)`). This was GUI-13 UX F2's fix text, landed
  with the side word kept.
- What the user sees (tie fixture): Checks says `G2 (1.25, 0.50) m on the face of Wall 1 -
  will be dropped`, and the same row's Where says `3 cm behind Wall 1 (dropped)`. "On the
  face" and "3 cm behind" cannot both be true, and neither says what to do.
- Fix (owner wording call): the reason for a non-inside drop becomes
  `within a cell of Wall n` in `gauge_drop_reason`. That one string feeds Checks, Run,
  Results and, after F2, the log. Where keeps its measured gap, since that is its job.
  Pinned strings change: `test_ui_setup_strip.py:580,597`, and whatever greps
  `on the face of` in `test_ui_run_screen` / `test_ui_results_screen` (list them in the
  plan).

**F5 - medium - 01 Setup tree and chain stage - the `Gauges` node is warn, but nothing on
it says which gauge.**
- Where: `setup_nodes.summaries:241-250` (caption), `setup_panel._sync_children` and
  `chain_stage._sync_children:417-423` (child rows, no state), `setup_tree._ChildRow:31`.
- What the user sees: an amber mark next to `2 · in front of Wall 1`. On a chain stage
  there is no gauge table, so clicking the node shows a PointList with no mark at all, and
  the gauge is named only on 00 Stage.
- Fix: the caption appends ` · G2 dropped` from `scaled_distance.is_dropped` (one
  `drop_rule` per case, as `any_dropped` builds it). `_ChildRow` gets a `warn` state
  (diamond and name in `warn`), set from the same rule in both `_sync_children`. Nothing
  in `fieldform.py` changes.

**F6 - medium - Chain stage 1 / any 1D case - a gauge beyond the domain radius is dropped
silently.**
- Where: `solver1d.py:146` and `foam/writer.py:445` filter `0 < r <= R` with no log line.
  `validate_case` has no 1D gauge check. `scaled_distance.any_dropped:283` and
  `outside_domain:110` return False for 1D, and `case_from_meta:57-64` uses the result's
  own radii as "entered", so Results numbers the kept gauges 1..n.
- What the user sees (scratch, native and blastFoam): stage 1 at the new 1.5 m seed with a
  gauge at r 2.0 gets no Checks warning, a green node and no log line. After the start,
  Run says `G2 dropped by the solver.` with no reason. On Results the kept G3 is shown
  as G2. A8 made this reachable on the default route: radius 1.5 m instead of 10 m.
- Fix: in `outside_domain`, 1D uses `0 < r <= radius_m`, the solvers' own test.
  `any_dropped` covers dim 1. `_validate_closing` (or the 1D block) warns
  `G2 (r 2.00 m) outside the domain - will be dropped`. `solver1d` logs the same line as
  2D/3D (strings only). The 1D meta keeps `gauges` as entered. Characterise first: the 1D
  baseline cases must stay byte-identical.

## 5. Quick wins (best value, least effort)

1. **F1:** Run computes the drop at `set_case`, so a dropped gauge is never a `waiting`
   row (`run_gauges._render`, about 10 lines plus one check).
2. **F5 (caption half):** ` · G2 dropped` in `setup_nodes.summaries`. One function covers
   both Setup and the chain stage.
3. **P1:** `where_text` appends ` (dropped)` to the `inside` / `on the face of` forms
   when `wall` is set (2 lines).
4. **F3:** `meta['gauges_dropped']` written by the UI at run start and read first by
   Results (no solver change).
5. **P2:** one ending for the drop line. Run adds `.` and Results does not
   (`run_gauges.py:886` vs `results_gauges.py:584`).

## 6. Parking (low - listed, not tasked)

- **P1 - 01 Setup, Where.** `inside Wall n` and `on the face of Wall n` carry no
  ` (dropped)` (`scaled_distance.py:259, 262`), while the gap and outside forms do. The
  warn colour is the only signal, and native can *keep* a gauge just inside an off-grid
  face (`validation.py:1736-1739`) under the same words in `muted`. This is colour-only,
  and at 1100 px the suffix elides anyway (QA F3, parked).
- **P2 - Run vs Results drop line.** The text is identical apart from the trailing `.`
  (Run). The Qt Run log pane shows the `[warn]` line in plain text (`run_panel.py:1487`).
  Only Messages colours it.
- **P3 - Run card header.** With `ElideRight` the forced-elide text is `Z 2.99 m…`, which
  reads as metres once `/kg^1/3` is cut. Keep the number and unit in their own label and
  elide only `· Wall n` (`run_gauges.py:527-531, 566-573`). The tooltip has the full text.
- **P4 - Tk Results.** The drop is named only in the figure footnote
  `Not shown: G2 - dropped by the solver` (black italic, no wall, `plots.py:427-432`). The
  Summary table has no line. The table labels use 3 decimals and `->`
  (`gauge_summary.py:96,118`), while the panel titles beside them use 2 decimals and `→`
  (`plots.py:413-419`). Tk work is the owner's pick (CLAUDE.md §9).
- **P5 - Tk clip check.** `_summary_clip_check` runs on fill and `<Map>`, not on
  `<Configure>` (`gui/results_panel.py:298-301, 731-745`), so a later resize does not
  add or remove the bar. This is moot at ≥ 1100 px per A5's measurements.
- **P6 - Run, blastFoam 3D live.** When x-only positions tie, `_x_only_tie` falls back to
  payload numbers (`run_gauges.py:227-228`), so kept gauges are renumbered against Setup
  for the live part of such a run. This is deliberate ("naming it would be a guess"), but
  it is the one place the entered number is not kept.
- **Chain default route (A8).** No UX finding of its own. Card 2 opens clean. The 1.5 m
  seed differs from 01 Setup's 10 m, and nothing says so, but `SEED_CAPTION` names only
  charge, material and solver as copied, so this is not misleading. Its side effect is F6.
